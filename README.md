# Idoconverter

Marketplace-ready product photos, prepared in the browser. Sellers drop a batch of photos, pick Amazon India, Flipkart, Meesho or custom settings, and get centred, pure-white, sized, renamed JPEGs in a ZIP with a pass/fail report.

- **Stack:** Next.js 15.5 (App Router), React 19, TypeScript, CSS Modules. No UI or image libraries.
- **Processing:** entirely in the visitor's browser, in a Web Worker (with a main-thread fallback). Nothing is uploaded.
- **Pages:** server-rendered per request (about 10 ms each locally) so every response carries a fresh Content-Security-Policy nonce; images are processed in the browser, so the server still does little work.
- **Design system:** `docs/DESIGN.md` ("Inspection desk"). Tokens live in `app/globals.css`.
- **Backend:** a small MySQL-backed API for early-access sign-ups, anonymous batch statistics and a health check. See `backend.md`.
- **Tools:** product photos for marketplaces (`/product-photos`) and a bulk image converter (`/tools/image-converter`).
- **Docs:** start at `docs/DOCUMENTATION_INDEX.md`; status in `docs/IMPLEMENTATION_STATUS.md`.

## Configuration

| Variable | Purpose |
|---|---|
| `NEXT_PUBLIC_SITE_URL` | Canonical domain, e.g. `https://idoconverter.com`. Set before building. |
| `NEXT_PUBLIC_WHATSAPP_NUMBER` | Digits with country code, e.g. `919876543210`. Shows the done-for-you service offer and WhatsApp links. Leave empty to hide them. |

Also set your real domain in `lib/config.ts` (`SITE.url`), which is used for page metadata.

Because this variable starts with `NEXT_PUBLIC_`, it is built into the page. Set it **before** building, and rebuild after changing it.

## Keeping marketplace rules accurate

Rules live in `lib/presets.ts`. Each preset has:

- `verification`: `"sourced"` (from the marketplace's own staff or help content) or `"unverified"` (third-party guides only)
- `source`: the text shown to users
- `checkedOn`: the date shown to users

When you confirm a rule in a seller panel, update the values and `checkedOn`. Flipkart and Meesho are currently **unverified**.

## How the processing works

1. Decode the image (EXIF orientation applied) and composite any transparency onto white.
2. Check the photo's edges. If less than 60% is white or near-white, the photo fails: it needs background removal, which isn't included.
3. Optionally flood-fill from the edges. Near-white becomes pure white; neutral-grey shadow edges fade smoothly instead of being cut. Coloured pixels stop the fill, protecting light product edges.
4. Find the product's bounding box, scale it to the target fill, and centre it on a white square.
5. Encode as JPEG, lowering quality until the file fits the size limit.
6. Flag anything worth checking: enlargement above 1.5×, a product touching the photo's edge, an undersized original, or a file still over the limit.

### Known limitations

- Busy or coloured backgrounds are flagged, not fixed. Background removal would need an AI API.
- Enclosed gaps, such as the inside of a mug handle, stay slightly off-white. The fill works inward from the edges, which is what protects white parts of products.
- Text, logos, watermarks, focus and "is this the right product" can't be checked automatically. The report says so.
- HEIC photos aren't supported; iPhones usually convert to JPEG when sharing.
- A "Pass" is a technical pre-check against published rules, not a guarantee of acceptance.

## Tested

Headless Chromium, production build:

- 100 photos up to 12 MP processed in about 76 s, with the page responsive throughout (work runs in the worker)
- Valid ZIP output; all background corners RGB 255
- No horizontal scrolling at 360, 768 and 1440 px, in light and dark mode
- Keyboard: menu and inspector sheet close with Escape; focus moves into the sheet and returns to the photo
- Long file names, damaged files, transparent PNGs, oversized photos and coloured backgrounds

Not yet tested on real devices: test on a mid-range Android phone and an iPhone (Safari) before launch.
